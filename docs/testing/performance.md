# 성능 측정

목표는 [architecture/non-functional.md](../architecture/non-functional.md) §성능의 **일반 읽기 p95 500ms 이하, 생성 요청 접수 1초 이하**이고, 같은 숫자가 [operations/monitoring.md](../operations/monitoring.md)의 지연 알림(`ProofuApiLatency`)에도 들어 있습니다. 이 문서는 그 숫자를 **실제로 재는 방법**입니다.

```bash
scripts/perf.sh                                   # 표당 2,000행, 10 VU, 30초
scripts/perf.sh --rows 20000 --vus 30 --duration 1m
scripts/perf.sh --api https://api.staging.example  # 이미 떠 있는 환경 대상
```

스크립트가 전용 워크스페이스를 시드하고(`infra/performance/seed.sql`), 헤더 인증·가짜 AI로 api를 띄우고, k6를 컨테이너로 돌립니다([`read-paths.js`](../../infra/performance/read-paths.js)). **목표는 k6의 threshold로 적혀 있어서 넘으면 스크립트가 실패합니다.**

재는 대상은 사용자가 실제로 여는 순서입니다: 대시보드 → 목록 6종 → 두 번째 페이지(커서) → 검색 → 상세, 그리고 초당 2건의 분석 요청 접수.

## 마지막 측정 (2026-10-15, 로컬 compose · Apple Silicon · 10 VU)

| 데이터 크기   | 읽기 p95 | 접수 p95 | 실패율 | 처리량      |
| ------------- | -------- | -------- | ------ | ----------- |
| 표당 2,000행  | 21.9ms   | 28.0ms   | 0%     | 1,315 req/s |
| 표당 20,000행 | 87.8ms   | 43.6ms   | 0%     | —           |

**이 숫자는 목표 달성의 증거가 아닙니다.** 노트북 한 대에서 로컬 데이터베이스를 상대로 잰 값이고, 네트워크·동시 사용자·관리형 DB의 지연이 빠져 있습니다. 쓰임새는 **회귀 탐지와 병적인 경로 발견**이며, 같은 스크립트를 배포 환경에 겨누면(`--api`) 그때의 숫자가 SLO 근거가 됩니다.

## 이 측정이 찾아낸 것

첫 실행에서 **대시보드가 17.8초** 걸렸습니다(표당 2,000행). 다른 엔드포인트는 전부 15ms 이하였습니다.

원인은 타임라인 쿼리가 화면에 보여 줄 **5건의 counts를 워크스페이스 전체에 대해 계산**한 것이었습니다 — `claim_sources`를 세 갈래 OR로 조인하는 CTE가 경력 기록 2,000건 모두에 대해 평가되었습니다. 보이는 5건으로 범위를 좁히자 **17.8초 → 65ms**가 되었습니다.

같이 확인한 사실 하나: `claim_sources (source_type, source_id)` 인덱스를 추가해도 **원래 쿼리는 여전히 17.9초**였습니다. 작업량이 워크스페이스 크기에 비례하는 구조였기 때문이고, 인덱스(V18)는 같은 방향으로 조회하는 다른 곳(경력·프로젝트 상세의 Claim 목록, 보존 정리)을 위한 것입니다.

회귀는 `ListQueryPlanTest`가 막습니다: 20,000행 워크스페이스에서 타임라인 쿼리가 **읽는 행 수가 500 미만**이어야 하고 큰 표를 순차 스캔하면 안 됩니다. 실행 계획 단언이라 시간 기반 단언처럼 들쭉날쭉하지 않습니다.

## CI에 넣지 않는 이유

공유 러너의 측정값은 이웃 작업에 따라 흔들려서, 실패하면 무시하게 되고 무시하는 게이트는 게이트가 아닙니다. 대신 **실행 계획**(`ListQueryPlanTest`, 매 푸시)이 구조적 회귀를 잡고, 이 스크립트는 릴리스 후보와 정기 점검에서 사람이 돌립니다([test-strategy.md](test-strategy.md)).
